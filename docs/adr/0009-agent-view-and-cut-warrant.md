# AgentView 卡片流 + 头尾意图推断 + 裁剪凭证 + 盲测 review

## 背景

三个问题推动了这组决定：

1. **注意力**：agent 全量接收 trace，注意力必然模糊。长 trace 塞给 LLM 只会得到平庸的判断。
2. **裁剪权**：不能让 LLM 直接「编辑」trace——不可复现、不可审计。LLM 只能产出结构化判断，裁剪动作由确定性代码执行。
3. **产品分歧**：做受约束的完整产品（web/GUI），还是高内聚低耦合的 CLI 工具、把自定义能力开放给用户？

## 决定

### 1. 产品形态：CLI + 声明式 CutProfile（不做 GUI）

「每个人想要的剪法不一样」本质是三个参数：标签保留策略、压缩率区间、span 约束。这是配置，不是产品形态。裁剪偏好收进 **CutProfile**（声明式 TS 类型 + 默认值），CLI 吃 profile 跑。

- 自定义面 = CutProfile + skill 文件（场景先验）+ adapter（新 trace 格式）
- **对话调优**（如果做）：agent 只能改 profile，然后流水线重跑——对话产出配置，确定性执行不变。M3 之后再说
- GUI/web 只有出现真实用户反复调 profile 时才值得做

与 ADR-0008 同一条原则：LLM 永远不进编排/执行路径。

### 2. 流水线主流程（五步）

```text
① 头尾意图推断   主 agent 只读头 1–2 turn + 验证点附近 turn（不是死板的末尾——
                  agent 干完正事常还有写文档/清理/闲聊），输出意图假设 v0
                  + 场景分类。~2k token，一次调用
② 逐窗打标       subagent 按卡片流逐窗读段（骨架注入 context），输出标签 + 置信度；
                  可回报骨架修正 → 代码合并成骨架 v1（意图是增量构建的，不是一次读出）
③ 裁剪凭证       主 agent（基于骨架 v1 + 各窗打标结果）写 JSON 凭证（CutWarrant）：
                  引用式——只决定「留哪些段」，不改写段内容
④ 确定性裁剪     代码执行凭证，产出剪后 trace
⑤ 盲测 review    review agent 只拿任务意图 + 剪后 trace（故意不给凭证/骨架），
                  答「怎么解决的、关键转折在哪」；确定性代码对照骨架判分；
                  缺失骨架点 → 代码回填对应段，再来一轮（最多两轮）
```

### 3. 裁剪凭证（CutWarrant）：引用，不是改写

- agent 只决定 segment 的 keep / collapse / drop
- 唯一允许的改写：死胡同压缩成一句话时写摘要
- 每条决策必须标注 source（规则名 / LLM）+ 置信度——这是「点开看删除理由」的数据来源

### 4. Review agent 的凭证：故意不给

对抗性的关键在盲。review agent 只拿意图 + 剪后 trace，不拿 CutWarrant 和骨架——拿了它会替裁剪辩护。判分对照物是从原 trace 来的骨架，由确定性代码比对。回填循环是 review 不止做门禁、还做闭环修正的具体形式，也是「保守不裁」兜底的实现。

### 5. AgentView：面向框架特化的 trace 结构体（最重要）

L0 之后物理分成两份：

- **RawTrace**：原文。保真、审计、Training Cut 用。LLM 永远不看全量
- **AgentView**：卡片流。LLM 唯一可见的形态

三层注意力分辨率，**默认给哪层由代码决定**：

| 档 | 内容 | 谁用 |
|----|------|------|
| line | 仅动作签名 + rep_of 指针（相似重试聚类） | 规则判定的噪音段 |
| card | 签名 + 结果 + 读写文件 + 首句 | 默认形态，洞 B 打标够用 |
| full | 原文 | 洞 B 用 read_segment 主动拉取 |

注意力闭环：LLM 从压缩索引起步、自己决定往哪放大（拉取式，不是推送式）。token 只花在它主动关心的段上。

卡片字段要么来自原文截取、要么来自规则计算，**不允许 LLM 参与生成**——AgentView 一旦有 LLM 写进去的东西，可复现性就没了。

### 6. 成本：算法能干的绝不给 LLM

| 用纯算法（TS，零 LLM） | 用 LLM |
|---|---|
| 规则打标（失败调用、重复读、相似重试——token Jaccard 聚类） | 头尾意图（一次，~2k） |
| 文件依赖图（读过的文件后来被改过 → 有效探索强信号，给洞 B 免费置信度） | 模糊段打标（规则清完约剩 30%） |
| 切段、span 检查、压缩率统计、骨架比对判分（可降档模型） | review（输入就是剪后 trace——剪得越好 review 越便宜，良性循环） |

粗账：500 段全量打标 ~150k+ token；本方案 ≈ 2k + 40k + 10k ≈ **1/5**。这个数字进 HTML 报告首页。

不引入 Python：「能被算法取代」的部分全部用 TS 实现，双语言栈零收益。
