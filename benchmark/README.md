# Benchmark 设计

> **一句话**：6 个单项、3 层结构。用乘法复合分把「压缩 ↔ 保真」锁死；用连贯性下限卡住跳步幻觉；用分档赛道防止只挑软柿子。

| 字段 | 内容 |
|------|------|
| 版本 | v0.2 |
| 日期 | 2026-09-10 |
| 状态 | **已收口**（公式与及格线）；M1 分档报分壳已落地 |

---

## 为什么要这样设计？

压缩和保真是天然对抗的：

- **全删** → 压缩率完美，但路径没了  
- **全留** → 保真完美，但等于没剪  

两边都能靠单项指标作弊。再叠加会上 Shilong 说的「基准容易被 hack」，所以：

1. 指标必须**成对绑定、互相牵制**——单项好看不算数  
2. 用**乘法复合分**堵住「全删 / 全留」  
3. 用**连贯性下限**堵住「跳步太远喂幻觉」  
4. 用**分难度赛道**分开报分，防止 cherry-picking  

---

## 三层结构总览

```text
第一层  6 个单项指标（自动评测）
   │
   ▼  全部及格后才算总分，否则 0
第二层  防作弊复合分（乘法）
   │
   ▼  另有：人类可读性盲测（不进自动 benchmark）
第三层  分难度赛道（短 / 长 / 多死胡同，分开报分）
```

---

## 第一层：单项指标（6 个）

| # | 指标 | 怎么测 | 及格 | 良好 | 备注 |
|---|------|--------|------|------|------|
| 1 | **压缩率** | 剪后 token ÷ 原 token | ≤30% | ≤15% | 单独看无意义，必须和 2 / 3 绑定 |
| 2 | **关键步召回率** | 原始里被标成「关键决策」的步骤，剪后还在的比例（人工 + 强模型双标） | ≥95% | ≥98% | **最硬的指标**；漏一个关键决策，因果链就断 |
| 3 | **重放成功率** | 干净环境里，agent 只按剪后路径重做任务，能否得到同一正确结果 | ≥90% | ≥95% | 最接近真值，也最贵；每次评测要真跑任务 |
| 4 | **QA 保真度** | 从原始 trace 自动出 N 个题（如「根因是哪行？」「第几步换思路？」），只给剪后版作答，算答对比例 | ≥85% | ≥92% | 重放的廉价替代，日常评测主力；定期和重放对齐 |
| 5 | **连贯性** | 相邻两步让裁判模型打 1–5 分：「从前一步能否自然推出后一步」 | 均分 ≥4.0，**且任一项不得低于 2** | 均分 ≥4.5 | 会上点名的坑；要卡**下限**，不能只看均值 |
| 6 | **处理成本比** | 剪辑自己花掉的 token ÷ 剪掉的 token | ≤30% | ≤10% | 工具不能是成本黑洞，否则方案不成立 |

### 阈值为什么不对称？

- **召回（95%）严于 QA（85%）**：漏关键步是结构性、不可逆的伤害；QA 答错部分题多半是细节问题，可容忍。错误成本不对称，阈值就不该对称。  
- **连贯性卡下限、不只卡均值**：一段「跳崖」断链会污染整条训练数据，均值再好看也救不回来。  
- **初期先定及格线，别急着定满分线**：MVP 能稳定过及格就有讨论价值；「良好」档等基线跑通后再校准。

## 第二层：防作弊复合分 + 人类可读性

### 复合分（进自动 benchmark）

**规则：6 个单项全部及格，才算总分；否则总分 = 0。**

```text
Score = 压缩率得分 × 关键步召回率 × 重放成功率
```

为什么用**乘法**而不是加权平均？

- 任何一项接近 0，总分就崩  
- **全删**（召回 → 0）拿不到分  
- **全留**（压缩率得分 → 0）也拿不到分  
- 作弊路径被堵死  

**压缩率 → 得分（分段映射，不奖励剪到 0%）**

| 压缩率 | 得分 |
|--------|------|
| 30% | 60 |
| 15% | 90 |
| 5% | 100 |

中间值线性插值即可；**不设「越短越高」到 0%**。

> 召回率、重放成功率在公式里用 0–1 小数（或百分数统一量纲）；实现时固定一种写法并写进评测脚本。

### 人类可读性（不进自动 benchmark）

| 测法 | 及格 |
|------|------|
| 给 3 个同事各 10 分钟读剪后版，复述 agent 思路 | 复述覆盖率 ≥80% |

每个版本手动跑一次即可，不进日常自动流水线。

## 第三层：分难度赛道

数据集至少三档，**分开报分，禁止合并平均**：

| 赛道 | 定义 | 作用 |
|------|------|------|
| **短 trace** | &lt;50 步 | 基本盘；重放成功率应接近 100% |
| **长 trace** | 200+ 步 | 主要价值区；压缩率主战场 |
| **多死胡同** | 人为构造或挑选、试错很多 | 试金石；死胡同识别是规则层弱项，专门暴露 LLM 打标层的价值 |

---

## 数据集规模建议

| 项 | 建议 |
|----|------|
| 每档 | 30–50 条 |
| 总计 | 100–150 条起步 |
| 报告 | 均值 ± 标准差，不要只报一个数 |
| 准入 | **只收带 Ground Truth 的成功 trace**（与产品准入一致） |

关键步的金标：建议 **人工 + 强模型双标**，争议样本仲裁后入库。

---

## 和 MVP 的关系

| 阶段 | Benchmark 用法 |
|------|----------------|
| **MVP（M1）** | 先把指标 1（压缩率）+ 指标 3 或 4（重放 / QA）跑通；关键步金标可以先小样本；复合分与三档赛道可先搭架子 |
| **M2** | 六项齐全；复合分作为发布门禁；短 / 长分开报 |
| **M3+** | 多死胡同赛道加满；人类可读性每个版本手跑；良好档阈值按基线校准 |

产品侧 MVP「只盯压缩率 + 保真度」仍然成立：这里的指标 1 +（3 或 4）就是那两件事的可操作版本；其余指标防止以后把基准 hack 掉。

## 怎么跑（M1 分档壳）

评分实现：`src/eval/benchmark.ts`（门槛、乘法分、分档表）。CLI 只扫盘、蒸馏、打印 JSON。

```text
# 推荐：无 mint 挂起风险，假 L4 打出 composite>0
node script/run-distill.ts bench --no-llm --fake-l4

# 真 mint（opt-in；会话硬超时 SESSION_CALL_TIMEOUT_MS）
node script/run-distill.ts bench --with-l4
```

- 扫 `short/` `long/` `multi_dead_end/` 下的 `*.jsonl`。**默认 `no_llm`**（即使 `.env` 有 mint 也不自动连网），避免过夜挂起。
- `--fake-l4`：注入 `FakeSessionBackend`（确定性 heal + verify），三档均可出现 `replay=1` / `composite>0`。
- `--with-l4`：才启用真 mint L4 / with_llm。
- **composite**：六项全过才算分，否则 `0`；有 skipped 且无 fail → `null`。公式 = 压缩率得分 × 关键步召回 × 重放（乘法）。三档**禁止合成平均**。
- 金标：先读 `data/raw/<trace_id>.key-decisions.json`，没有再读样本旁的 `<stem>.key-decisions.json`。没有金标 → 关键步召回 `skipped`，M1 **不算硬挂**。
- stdout 一行 JSON + `benchmark/out/scoreboard.md`。
- 现有样本：`short/`（add-fix + fluff-heavy）、`long/long-debug`、`multi_dead_end/many-retries`；workspaces 见 `manifest.json`。

```text
benchmark/
├── README.md          ← 本设计文档
├── datasets/
│   ├── short/         ← M1 合成小样
│   ├── long/          ← 可空
│   └── multi_dead_end/
├── workspaces/        ← L4 真实小仓 + manifest
├── suites/            ← 各指标评测脚本 / 配置（尚未）
└── reports/           ← 跑分结果（均值±标准差）
```

## L4 重放工作区（真实小仓）

合成 replay≈0 的根因：bench 以前开 L4 会话却**没有可改的仓库 cwd**，真模型只能回 success=false，六项里 replay 挂 → composite 被乘成 0。

现约定：

```text
benchmark/workspaces/
  manifest.json          # trace_id → workspace key
  add-fix/              # short/long/multi 共用小仓（坏掉的 add.ts + verify）
  mul-fix/              # 第二小仓（坏掉的 mul.ts；尚未挂 track 样本）
```

- `runOptionalL4` / `bench` 解析 manifest，**物化临时副本** 作 replay cwd；成功与否经 `verify[]` 闸门。
- `--fake-l4`：确定性 heal（`add.ts` / `mul.ts`）+ verify，证明 composite 通路。
- **真 mint**：`TRACE_DISTILLER_MODEL_L4` + gateway + `bench --with-l4`；模型须在副本里改文件并通过 verify。详见各 workspace README。
